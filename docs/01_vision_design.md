# 1단계 설계안: 비전 레이어 (두 손 추적과 손목 자세)

2026-10-12 초안입니다. 코드를 쓰기 전에 좌표계, 토픽, 검증 방법을 먼저 정합니다.
여기서 정하는 손목 자세를 3단계에서 팔 EEF 가 그대로 따라가므로, 이 문서가 3단계까지의 계약 역할을 합니다.

---

## 1. 범위

**하는 것**

- 카메라 한 대로 두 손을 동시에 추적하고, 좌우를 구분해서 손별로 발행합니다.
- 손마다 21점 world landmark 를 지금 손 저장소와 같은 형식으로 발행합니다. 손 파이프라인이 수정 없이 받을 수 있게 하기 위해서입니다.
- 손마다 손목 자세(위치와 방향)를 카메라 좌표계에서 발행합니다.

**하지 않는 것**

- 카메라 좌표계를 로봇 베이스 좌표계로 옮기는 일은 3단계에서 합니다.
- 손 저장소는 수정하지 않습니다. 1단계 검증은 ROS 리매핑으로 기존 노드에 연결해서 합니다(5장).

## 3. 설계 결정

### 3.1 MediaPipe 에는 뒤집지 않은 원본 영상을 넣습니다

지금은 화면을 보기 편하도록 뒤집은 영상을 그대로 MediaPipe 에 넣고 있습니다. 손가락 리타게팅만 할 때는 리타게터가 x 를 되돌리면 되므로 문제가 없었지만, 손목 위치를 카메라 좌표계에서 구하려면 영상과 카메라 내부 파라미터가 서로 맞아야 합니다. 뒤집힌 영상으로 계산하면 이후 모든 좌표 변환에 "x 가 뒤집혀 있다"는 예외가 따라다니게 됩니다.

- 원본 영상을 MediaPipe 에 넣고, 화면 표시용으로만 뒤집습니다.
- MediaPipe 는 입력 영상이 거울상(셀카)이라고 가정하고 handedness 를 판단하므로, 원본 영상에서는 `Left` 와 `Right` 라벨이 실제 손과 반대로 나올 것으로 예상합니다. 노드에서 라벨을 맞바꿉니다. **이 가정은 실측으로 확인합니다**(6장 V1).
- 그 결과 발행하는 world landmark 는 이미 실제 좌우가 맞는 상태이므로, 기존 리타게터는 `--no-undo-mirror` 로 띄웁니다.

### 3.2 좌우 구분

처음에는 단순한 규칙으로 시작하고, 실측에서 라벨이 뒤바뀌는 빈도를 본 뒤에 필요할 때만 추적 로직을 더합니다.

1. MediaPipe handedness 점수가 문턱값(초기값 0.8)을 넘는 손만 받습니다.
2. 두 손이 같은 라벨로 나오면, 영상 안의 x 위치로 정합니다. 카메라를 마주 본 작업자의 오른손은 원본 영상의 왼쪽에 보입니다.
3. 한 손만 보이면 그 손의 토픽만 발행하고, 보이지 않는 손의 토픽은 발행을 멈춥니다. 이전 값을 반복해서 내보내지 않습니다. 지금 손 저장소의 방식과 같습니다.

두 손이 교차하거나 겹칠 때 라벨이 흔들릴 가능성이 높습니다. 이 경우는 6장 V2 에서 따로 측정합니다.

### 3.3 손목 위치: RGB 한 장에서 PnP 로 구합니다

MediaPipe world landmark 는 미터 단위이지만 원점이 손 중심에 고정되어 있어서, 카메라에서 손까지의 거리는 들어 있지 않습니다. 같은 프레임의 영상 좌표(픽셀)와 world landmark(손 기준 3D)를 짝지어 `cv2.solvePnP` 를 풀면 손이 카메라 좌표계에서 어디에 있는지(R, t)를 얻을 수 있습니다.

- 필요한 것: 카메라 내부 파라미터. 체커보드로 한 번 보정해서 `config/` 에 저장합니다. 보정 도구를 이 저장소에 둡니다.
- 사용할 점과 알고리즘: **21점 전체와 `SOLVEPNP_SQPNP`** 를 씁니다. 처음에는 손바닥 5점(0, 5, 9, 13, 17)을 우선 쓸 계획이었지만, 합성 손으로 측정해 보니 OpenCV 4.10 에서는 5점만으로 안정적으로 푸는 알고리즘이 없었습니다(2026-10-12).

  | 입력 | SQPnP | ITERATIVE |
  |---|---|---|
  | 손바닥 5점, 노이즈 없음 | 평면이면 최대 276 mm 오차 | 평면이면 정확, 평면에서 1~3 mm 만 벗어나도 예외 발생(DLT 는 6점 이상 필요) |
  | 21점, 1 px 노이즈, 굽은 손 | 중앙값 1.9 mm, p95 7.4 mm | 중앙값 2.4 mm, p95 1356 mm |
  | 21점, 1 px 노이즈, 편 손 | 중앙값 1.8 mm, p95 7.4 mm | 중앙값 1.8 mm, p95 6.9 mm |

  이 선택은 `tests/test_wrist_pose.py` 의 노이즈 테스트가 지킵니다. ITERATIVE 로 바꾸면 이 테스트가 실패합니다.
- 한계: 거리(카메라 z 방향)는 MediaPipe 가 추정한 손 크기에 비례해서 틀어집니다. 실제 손이 MediaPipe 의 평균 손보다 10% 크면 거리가 대략 10% 가깝게 나옵니다. 작업자별 배율 보정 한 번으로 줄일 수 있지만, 프레임마다 생기는 떨림은 남습니다.

깊이 카메라가 있다면 손목 픽셀의 깊이 값을 읽는 쪽이 훨씬 정확합니다. 7장 질문 1 을 보세요.

### 3.4 손목 방향: 손바닥 프레임

동료 프로젝트의 `canonical_axes` (`~/V6_Teleoperation/src/v6f_teleop/hand/mano.py`)와 같은 점을 씁니다. 리타게팅과 팔 추종이 같은 손 프레임을 공유해야 나중에 손가락과 팔의 움직임이 서로 어긋나지 않기 때문입니다.

- z: 손목(0)에서 중지 MCP(9) 방향. 손이 뻗은 방향입니다.
- y: 약지 MCP(13)에서 검지 MCP(5) 방향으로 만든 보조 축을 z 에 직교화합니다.
- x: y 와 z 의 외적. 손바닥 법선입니다.

**좌우 손의 차이**: 위 식을 양손에 그대로 쓰면 회전행렬은 양손 모두 올바르게(det = +1) 나오지만, x 축이 한 손에서는 손바닥 쪽, 다른 손에서는 손등 쪽을 가리킵니다. 리타게팅에서는 이 성질이 의도된 것이지만, 팔이 따라갈 자세에서는 축의 의미가 양손에서 같은 편이 다루기 쉽습니다. 그래서 왼손에서는 보조 축의 부호를 뒤집어 **양손 모두 x 가 손바닥 바깥쪽을 향하도록** 정의합니다. 이 차이는 손목 자세 발행에만 적용하고, 리타게팅에 넘기는 21점은 건드리지 않습니다.

- 회전: 손바닥 프레임을 world landmark 좌표계에서 만든 뒤, PnP 로 구한 R 로 카메라 좌표계에 옮깁니다.
- MediaPipe world landmark 의 축 방향(예: y 가 아래를 향하는지)은 문서만으로는 확신할 수 없어서, 실측으로 확인합니다(6장 V3).

### 3.5 토픽과 메시지

손 하나당 같은 이름 묶음을 네임스페이스로 나눕니다. 2단계에서 손 파이프라인을 `/left`, `/right` 로 두 벌 띄우는 구조와 바로 맞물리게 하기 위해서입니다.

| 토픽 | 형식 | 내용 |
|---|---|---|
| `/{left,right}/allegro/vision/world_landmarks` | `std_msgs/Float32MultiArray` (63) | 기존과 같은 형식. 단 좌우가 이미 맞는 상태 |
| `/{left,right}/wrist_pose` | `geometry_msgs/PoseStamped` | 카메라 광학 좌표계(`camera_optical`) 기준 손목 위치와 손바닥 프레임 |
| `/camera/image_raw` | `sensor_msgs/Image` | 원본 영상. 대시보드가 카메라를 다시 열지 않고 이 토픽을 받게 할 수 있습니다 |

- `PoseStamped` 의 `header.stamp` 는 프레임을 받은 시각으로 채웁니다. 4단계에서 팔, 손, 영상을 시간으로 맞춰 기록할 때 이 값이 기준이 됩니다.
- 손목 자세에 PnP 재투영 오차와 handedness 점수를 같이 실어 보낼지는 V4 측정을 보고 정합니다. 처음에는 넣지 않습니다.

### 3.6 실행 환경

- 새 저장소에 `.venv` 를 따로 만들고 `--system-site-packages` 로 시스템 ROS 의 `rclpy` 를 씁니다. 손 저장소의 방식과 같습니다.
- 버전은 손 저장소와 맞춥니다: `mediapipe==0.10.14`, `numpy<2`, OpenCV. 설치 전에 목록을 다시 보여 드리겠습니다.
- 해상도는 1280x720 MJPG 로 올리는 것을 검토합니다. PnP 의 거리 정확도가 픽셀 해상도에 영향을 받기 때문입니다. 대신 MediaPipe 처리 속도가 떨어질 수 있어서 V5 에서 비교합니다.

## 5. 기존 손 파이프라인과의 연결(1단계 검증용)

손 저장소를 고치지 않고, 리타게터를 띄울 때 토픽을 리매핑해서 새 비전 노드의 출력을 받게 합니다.

```bash
retargeting_node_v3.py --hand right --no-undo-mirror \
  --ros-args -r /allegro/vision/world_landmarks:=/right/allegro/vision/world_landmarks
```

토픽 이름을 상대 경로로 바꿔 네임스페이스로 여러 벌 띄우는 변경은 2단계에서 손 저장소에 넣습니다. 인수인계 문서에서 손 저장소가 받기로 한 변경의 범위가 여기까지입니다.

알려진 충돌: 지금 `run_dashboard.sh` 는 대시보드가 카메라를 직접 엽니다. 새 비전 노드와 동시에 띄우면 카메라를 두 프로세스가 열려고 해서 실패할 수 있습니다. 1단계에서는 리타게터와 브리지만 따로 띄워서 검증하고, 대시보드가 `/camera/image_raw` 를 받도록 하는 변경은 2단계에서 다룹니다.

## 7. 정해 주셔야 할 것

1. **카메라.** 지금 연결된 카메라는 노트북 내장 웹캠 하나입니다. 팔이 손목 자세를 따라가려면 카메라가 고정되어 있어야 하는데, 노트북 화면 각도를 바꾸면 좌표계 전체가 같이 움직입니다. RealSense 같은 깊이 카메라나 고정할 수 있는 외장 카메라가 있다면 1단계부터 그 카메라로 설계하는 편이 낫습니다. 대시보드의 자동 탐색 코드가 RealSense 를 먼저 찾도록 되어 있어서, 예전에 쓰신 적이 있는지 확인하고 싶습니다.
2. **손목 위치의 용도.** 3단계에서 팔이 손목의 절대 위치를 따라갈지, 클러치를 잡은 순간부터의 상대 이동만 따라갈지에 따라 V4 의 기준이 달라집니다. 상대 이동이라면 거리의 절대 오차보다 떨림과 배율 일관성이 중요합니다. 지금은 상대 이동을 가정하고 있습니다.
