# R3 결과 v2: 재시도 (추종 노드 v3), 자동 정지 실패, 고친 것

- 날짜: 2026-10-19
- 실행과 분석: Claude Opus 5.5 (총괄). 사용자 승인 후 진행했고, 사용자가 로봇을 지켜봤습니다.
- v1 (`r3_left_wrist_follow.md`): 손 방향 전환, 첫 시도 두 번, 추종 노드 v3 를 만든 이유

## 1. 재시도 결과

설정: `arm_follow_node_v3.py --position-only --scale 0.5 --radius 0.07 --max-joint-speed 0.3`, 브리지 v2 `--max-excursion 0.3`, `timeout -s INT 38`.

| 구간 | 결과 |
|---|---|
| 처음 12.3 s | **추종이 좋았습니다.** 손 × 0.5 대비 팔 끝 상관: 앞뒤 +0.96, 좌우 +0.95, 상하 +0.99. 팔 끝 범위 77 / 11 / 44 mm |
| 12.3 s 이후 | 추종 노드 명령이 브리지 상자(0.3 rad)를 넘었고, 이후 브리지가 모든 명령을 무시했습니다. 팔은 정지 |
| 손 검출 | 356/893 프레임. 손이 자주 화면을 벗어났습니다 |

**범위를 넘은 이유:** 손을 놓쳤다가 다시 잡을 때마다 클러치가 다시 걸렸습니다. 그때마다 v3 의 반경 중심이 그 순간의 팔 위치로 옮겨졌고, 이것이 쌓여 팔 끝 명령이 157 mm, 관절 명령이 0.58 rad 까지 갔습니다.

## 2. 자동 정지 실패 (안전 사고)

`timeout -s INT 38` 이 브리지를 멈추지 못했습니다. 브리지는 약 40초 더 떠 있다가, 제가 PID 로 SIGINT 를 다시 보내자 정상 종료하고 팔을 state 4 로 두었습니다.

그 사이 상황은 이렇습니다.
- 팔은 정지 상태(state 4, 오류 0)였습니다.
- 브리지는 범위 밖 명령을 무시하느라 아무것도 보내지 않았습니다.
- 그래서 실제 위험한 움직임은 없었습니다.

하지만 "30초 뒤 정지"라는 약속이 지켜지지 않았습니다.

v2 의 신호 처리기는 메인 스레드가 어디에 있든(rclpy 콜백 안이든 SDK 호출 안이든) 그 자리에서 KeyboardInterrupt 를 던졌습니다. 이 예외가 어디서 삼켜졌는지는 확정하지 못했습니다. SDK 의 `except:` 두 곳은 우리 호출 경로가 아니었습니다. 그래서 정지가 신호 전달 시점에 의존하지 않도록 구조를 바꿨습니다.

## 3. 고친 것

**`arm/xarm_bridge_node_v3.py`**
- `--duration` 필수: 시간이 되면 브리지 **스스로** 팔을 멈추고 종료합니다.
- 신호 처리기는 표시만 남깁니다. 메인 루프가 50 ms 마다 표시와 마감 시각을 확인합니다.
- 신호 처리기를 로봇 연결 **전에** 설치하고, 연결 중에 정지가 오면 모터를 켜지 않습니다.

**`arm/arm_follow_node_v4.py`**
- 반경 중심을 **시작 자세에 고정**했습니다. 클러치를 다시 걸어도 움직이지 않습니다.
- `--joint-box`: IK 자체가 시작 자세 ± (상자 − 0.02) rad 안에서만 풉니다. 브리지 상자를 넘는 명령이 나오지 않습니다.

## 4. 검증 (dry run, 팔 미구동)

| 시험 | 결과 |
|---|---|
| `--duration 5` | 5.4 s 에 스스로 종료 |
